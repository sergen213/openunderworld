# Lara's player state chart (lara.drm)

## Runtime

How tru.exe runs the state charts stored in Lara's player data (lara.drm ObjectBase +0xC8 data block). Port:
`src/game/Chart.{hpp,cpp}` (loader, `ChartRuntime`, `Registry`, `chart-dump`), `src/game/ChartShadow.cpp` (shadow
mode), `src/game/chart/<Family>.cpp` (conditions / actions, listed in `src/game/chart/Families.cpp`). Tests:
`tests/test_chart.cpp` (`ou_chart_tests`). Evidence tags: [O] read in tru.exe / the data, [I] inferred, [U] open.

### Data layout [O]

All offsets below are from the start of the player data block.

- Two chart headers of 0x28 bytes: **+0x12500** Lara (agent 0, 1445 states / 2374 transitions / 69 events) and
  **+0x12528** the upper body / weapons (agent 1, 103 / 203 / 14). Header: +0 s16 root state, +2 s16 agent index,
  +4 -> linked chart (the upper chart points at Lara's), +8 u16 state count, +0xA u16 transition count, +0xC ->
  states[], +0x10 -> transitions[], +0x14 -> events[] (the event count is the run of pointers; Lara's states reference
  events 0..68), +0x18 / +0x1C the state / transition record pools. Both charts' root is S0.
- State (0x28): +0 s16 id, filled lazily with -index on first entry (0x787890); +2 s16 anim request kind
  (0x444BA0: 0 / 1 / 2, 2 = mirror-aware); +4 s16 anim request (< 0 none); +6 s16 parent; +8 u16 (always 0 in
  lara.drm; 0x781FA0 tests it up the chain while applying properties); +0xA/+0x14 properties; +0xC/+0x18 action ids
  (u16); +0xE/+0x1C transition indices; +0x10/+0x20 event indices.
- Property (8): {u16 id, u16 type, u32 value}. Value readers: bool 0x783770 (type 2 byte, 0x10 int, 0x29 tuning
  record), int 0x783590 (2 byte; 7, 9, 10, 11, 0x10, 0x11, 0x17, 0x1A, 0x1D, 0x23 int; 0xC / 0xD float truncated;
  0x29 record), float 0x783680 (0xC / 0xD float, 0x10 / 0x11 int, 0x29 record). Type 0x29 points at a tuning record
  {u32 type, value} (1 int, 3 float frames, 4 float distance, 5 bool). Type 0x2B takes the linked chart's current
  value of the property it names (0x785B90).
- Transition (0x14): +0 s16 target, +2 u16 flag count, +4 u16 condition count, +8 -> s16 flags, +0xC -> conditions.
- Condition (8): {s16 group, s16 id, s16 value, u8 flags}. `id` selects the function; `value` is its parameter;
  flags bit 0 negates (each condition function applies it itself). The group is only the family number (100 buttons,
  150 action flags, 400 stick, 500 player, 600 markup, ...) except **1000**: then `value` is an index into the chart
  variables (0x7820E0 int: floats truncated, bools 0 / 1; 0x782060 float). Functions that read a mode from `value`
  get 1000 itself (0x781FF0), which no mode case handles.
- Event (0x10): {u32 event id, u8 result when a transition fired, u8 result when none did, u8 record, u16 count,
  -> {s16 transition, s16}[count]}.
- Chart variables: a run of 400 pointers to tuning records, pointed at by data +0x18CC (at run time tru.exe reaches
  the same table through the instance's object, 0x782B40 / 0x7820E0). E.g. variable 344 = 632.11, 347 = 4.0, 193 = 10.
- Anim request: kinds 0 / 1 index the object's anim patterns (0x444BA0 -> 0x4428A0; anim::animPatterns; e.g. S1280
  request 39 = `ng_land_hard`). Kind 2 is no pattern index (S65's request 99 is not `obj_no`): 0x443720 -> 0x43E250
  selects node `request` of the object's anim graph, ObjectBase +0x4C count / +0x50 table of {u32 DTP id, u32} (lara:
  218 nodes; not the cdc AnimGraph of ObjectBase +0x64 / +0x68, which stays 0), and runs the node's enter program
  (DTP header +4; exit program +8) on the anim graph VM 0x432B20 (stack bytecode: 2 push, 0x47..0x52 arithmetic /
  compares, 0x63 / 0x64 jumps, 0x65 native call, 0x7B return). Module 0's natives (0x8AC128 -> 0x88F238): 0 Play
  (0x448100: pattern, flags, two floats), 1 IsPlaying (0x43B390: pattern or -1, frame range, flags), 5 /
  6 open / close a blend node. E.g. node 213 (S245, the stick jump): if pattern 52 (`ng_standing_jump`) is playing,
  Play 680 (`ng_planted_jump_forward`) flags 1, else flags 2 [O: data, decomp]. Play (0x448100) builds a 7-word record
  (pattern, flags, its two float arguments rounded to override the pattern's start +0x1A / blend +0x19 when >= 0) and
  queues it (0x446BD0: flags & 7 = 1 start in phase with the playing clip, 2 flush the queue first, 4 conditional, 0
  queue); 0x444EA0 hooks the layer's end callback (0x43E0C0) and 0x443430 plays each record through 0x4428A0, so a
  kind-2 clip starts like a pattern request (below) [O]; the chart's end notification comes when the queue drains
  (0x43E0C0) [O]. Node 46 (S40 idle) plays 685 `ng_idle` with sprint
  stamina left, else 691 `ng_idle_break_hot`; node 99 (S65) 716 `ng_run_start`, else 717 `ng_run_exhaust`: module 1's
  native 76 (0x6EA1E0) is 0x74FD70 on the stamina record at agent +0x460, condition 0x205's test (ctx.canSprint()).
  A node that plays nothing keeps the clip and its clock. Ours: `ChartRuntime::resolveRequest` runs the program (both
  ways on an unported native's value, resolved when they agree); an unresolved node has no clip clock. Our script VM
  (src/script) shares the opcode numbering but is not this VM (its 0x65 calls a method on a receiver). A pattern's
  clip starts at (start - blend) frames, uncut (`Request::startFrame`), so that it stands at the pattern's start frame
  when the crossfade ends [O-runtime, W/chart/wine/*_anim: 0x441FB0's (start, blend) arguments and the clip time they
  leave: 680 (100, 400) -> -300 (S245 15 ticks), 678 (100, 200) -> -100, 52 (600, 600) -> 0, 954 (400, 300) -> 100].
  The blend is the previous pattern's +0x1B when it set one (layer +0x314, 0x4428A0; 1460 trans_pose_U -> 952 at blend
  0, time 400: S535 38 ticks). For the first clip a blend > 0 with a key longer than a frame and start inside it moves
  start to that key and lengthens the blend by the move (1463: (207, 207)). 0x4428A0's other branch (start - blend cut
  at 0, blend 0) needs the layer's +0xA4 == 0 or +0xA8 > 0 with +0xAC == 0; Lara's layer reads 1 / 0 / 1 in every
  recording, so ours never takes it. AnimationEnded (0xC9, 0x783840) polls the clip time against 0x438930 (keys x time
  per key, rounded up to whole keys, `Request::lengthFrames`).

### Function registry [O]

Conditions, property handlers and actions live in one splay tree of "SC enum" nodes keyed by s16 id (global tree at
manager 0xFAF030 +8, per-agent override tree at agent +0x520; lookups 0x783F50 / 0x784C50). A node holds: +0x18
condition function, +0x1C property handler, +0x20 Entry, +0x24 Reentry, +0x28 PreAnimEntry, +0x2C PreAnimReentry,
+0x30 Exit, +0x34 Process, +0x38 the property record in force, +0x3C the condition cache {agent, frame, value}, +0xA
an entry/exit balance byte (warnings only). Tables (filled by 0x784EE0 / 0x784F60 / 0x784FE0 for the base,
0x785120 / 0x785390 / 0x785600 per agent, from 0x768B60):

| | conditions {id, group, fn} | property handlers {id, fn} | actions {id, Entry, Reentry, Exit, Process, PreAnimEntry, PreAnimReentry} |
|---|---|---|---|
| base | 0x8B57E0 | 0x8B6650 | 0x8B4200 |
| Lara (agent 0) | 0x8B2CE8 | 0x8B2280 | 0x8B0A50 |
| upper body (agent 1) | 0x8B2838 | 0x8B26E0 | 0x8B1E00 |

The action tables' column order is not the node's: 0x784FE0 -> 0x7843A0 stores record words 1..6 at node +0x20 Entry,
+0x24 Reentry, +0x30 Exit, +0x34 Process, +0x28 PreAnimEntry, +0x2C PreAnimReentry. `ActionFns` follows the node
order; register a table row as `{w1, w2, w5, w6, w3, w4}`.

An agent table entry copies the base node's functions, then overrides its own. Base entries that are only
placeholders point at 0x782140, which logs "unhandled" and returns **true**; every id Lara's chart uses is overridden
or real. Ours: an id without a registered function is **false** (whatever the negation) and counted
(`ChartRuntime::stats`), so a missing port can never open a transition.

Generic base conditions: 0x1 (0x782700) always true; 0x14 (0x783B70) state time: (int) agent +0x508 >= value
(0x782B40 mode 1; mode 2 is <=, mode 0 ==); 0xC9 (0x783840) AnimationEnded on the end counter +0x24 (mode 0: < 1,
1: > 0, 2: == 0, 3: == 1; it also counts the clip's time having reached its length while the counter is under 2).
Float compares go through 0x783BD0 (mode 1 >=, 2 <=, 0 within epsilon 0x8454C4).

### Agent and tick [O]

Agent (0x7873C0; Lara's at player +0xF10, the upper chart's at +0xF14): +4 -> chart header, +8 instance, +0x24 anim
end counter, +0x500 active, +0x504 total time, +0x508 **state time**, +0x50C frame counter (condition caches are
valid while it is unchanged), +0x510 current state, +0x514 queued transition, +0x518 last transition, +0x51C cleared
on every change [U], +0x520 agent enum tree, +0x524 / +0x528 linked child / parent agents, +0x53C defers flag-7
transitions [U what sets it], +0x70 / +0x74 the move-dir / move-speed conditions' last zones.

- **Per game frame** (0x768C50 ticks agent 0 then agent 1; 0x787E60): if active, +0x504 and +0x508 += timeMult
  (30 Hz frames: 0.5 per 60 Hz frame), the end counter steps away from zero (< 1: -1, else +1), Process of every
  action of the state's chain (parent first, 0x7857D0), then the evaluation 0x787C50. The chart therefore evaluates
  every game frame, with times in 30 Hz frames. [U] where 0x768C50 sits in the frame relative to the anim and
  physics updates (it is reached through a pointer, 0x85E1D0).
- **Start** (0x787E00): current = root, active, properties applied, anim request, Entry of the root chain's
  actions (no PreAnim pass), then one evaluation.
- **Evaluation** (0x787C50): frame counter + 1; find a transition (0x787570) and change (0x787890); after a change
  to a new state the search repeats in the same frame only while property **0x65** reads true (each repeat bumps the
  frame counter).
- **Finding** (0x787570): first the queued transition, if it is flagged 1 and the end counter is exactly 1, or
  flagged 7 and +0x53C is clear. Then the state's **own transitions in stored order; the first whose conditions all
  hold wins** (0x785920 evaluates the conditions in order and stops at the first false one). Only if none holds,
  the parent's (recursively up to the top). A winner flagged 1 while the counter is not 1, or flagged 7 while
  +0x53C is set, is queued (+0x514) instead and nothing fires.
- **Change** (0x787890): flag 6 takes the queued transition instead. Target < 0 keeps the current state. Same state:
  a positive end counter is reset to 0, and without flag 4 nothing else happens (no re-entry; last / queued updated).
  Otherwise, in order: Exit of the old chain's actions (parent first) that the new chain does not also run
  (0x7859A0 / 0x781DC0); current = target; flag 2 sets the instance mirror bit (+0xF4 0x20), flag 5 clears it;
  properties (below); PreAnimEntry for actions new to the chain, PreAnimReentry for the others (0x785AE0); the anim
  request plays and the end counter becomes 0 (0x783470); Entry / Reentry likewise (0x785A30); state time 0, queue
  cleared, last transition = this one.
- **Properties** (0x785E70 -> 0x785CC0): the new state's properties, then its parent's, up the chain, then (if the
  chain's top is not the root) the root's chain; a pass stamp lets each id be applied **once per pass, so the most
  derived state wins**. Each applied property runs its handler (+0x1C) and becomes the id's value in force. Ids none
  of them sets keep their old value.
- **Animation end** (0x768CF0, from the anim controller's notifications 0x7181A0 / 0x718520 reasons 1 / 2 / 8 and
  anim event command 0x72 in 0x716F30): if the end counter is negative it becomes 1, the evaluation runs at once
  (flag-1 transitions and the queued one can fire now), and if the state time is above 0 event **0x15** is posted.
  The counter then grows each frame, so flag-1 transitions are a one-frame window.
- **Events** (0x787CD0 posting, 0x7876E0 handling): frame counter + 1; the state's handlers of the event id (else the
  nearest ancestor's, else the root chain's) in order, each handler's transitions in order; the first that holds
  wins. A winner flagged 1 or 7 is queued. The result byte of the handler decides whether the post counts as
  handled. A fired transition changes state, with the same property-0x65 chaining as the evaluation. Event ids in
  Lara's chart: 21 (0x15), 64, 133, 145, 159, 235, 262, 269, 274, 284, 455, 457, 458, 466, 468, 469, 470.

### Input timing [O]

Lara's conditions 0x65..0x6E (0x760A30..0x760B30) each read one input action through 0x7607C0: 0x65 action 52
(Jump), 0x66 50 (Crouch), 0x67 42 (Sprint), 0x68 / 0x69 99 (Interact), 0x6A 112, 0x6B 34, 0x6C 25 (Manual Aim),
0x6D 28, 0x6E 79. Value: 1 on the press frame, frames held + 1 while down, -1 on the release frame, -1 - frames
while up (frames = ms x 30 / 1000, at least 1); mode (table 0x7609C0) 0 up, 1 down, 2 released, 3 pressed, 0x65 held
longer than player data +0x6E2 (15). Conditions 0x96 / 0x97 / 0x98 (= 0x9E) / 0x99 (0x760B50..0x760CB0) test the
flags of the action `value` names: down, not down, pressed, released. The stick level 0x191 (0x761CD0 -> 0x786AF0)
puts the stick magnitude (player globals 0xFADFB0 -> +0xB0 -> +0x18 [I: 0..1]) in zones 1 / 2 / 4 / 8 by the
thresholds of properties 0x20A / 0x20B / 0x20C (Lara: 0.10 / 0.70 / 0.91), raised by the hysteresis 0x20D / 0x20E /
0x20F (0.02 each) above the last frame's zone and lowered below it; values 401..404 test zones 1 / 2 / 4 / 8 (405
"sprint" tests 8). Fall 0x1E (0x764B40): player +0x6DC - z >= value (float compare).

### Ours

- `ChartRuntime` follows the order above: `tick` = 0x787E60, `evaluate` = 0x787C50, `find` = 0x787570, `holds` =
  0x785920, `change` = 0x787890, `post` = 0x787CD0, `animEnded` = 0x768CF0. The requested clip's clock is kept by the
  runtime itself (pattern start frame, rate, length from the clip header) and calls `animEnded` when a one-shot clip
  reaches its end or a loop wraps [I: notification order].
- **Units**: the chart's times (+0x508 state time, condition 0x14, clip clock, flags of 0x783840) count 30 Hz frames;
  a 60 Hz game tick adds timeMult = 0.5. Traces count 60 Hz ticks (`stateTicks`), so N chart frames = 2N ticks.
  Example, Wine `run_jump_bedroom` (W/chart/wine/jump): S63 `ng_run_start` from tick 10, the Jump press at tick 40
  leaves it for S281: a dwell of 30 ticks = 15 frames, ended by the press, not by the clip. The clip (request 716,
  27 frames from frame 2) would end it after 25 frames = 50 ticks (T246 -> S65, tick 60). Ours, with the clip clock
  starting at (start - blend), dwells the same up to the press (checked by driving S63 with the case's inputs); before
  that fix the clip was taken from frame 6 and S65 came after 4 ticks. Taking the jump itself needs S63 T47 / T172
  and S64 T60 / T52, whose conditions 0x836, 0x192, 0x12D are family work.
- One time step: `ChartRuntime::tick(ctx, timeMult)` stores it in `ctx.timeMult` (gameTracker_timeMult, 30 Hz frames)
  before anything runs; conditions and actions read `ctx.timeMult`, never a clock of their own. `ChartRuntime::enter`
  puts the chart in a state without a transition (tests / tools).
- Generic conditions ported (`src/game/chart/Generic.cpp`): 0x1, 0x14, 0xC9, 0x65..0x6E, 0x96..0x99 / 0x9E, 0x1E,
  0x191. Everything else waits for its family.

### Shadow mode

`ou-game ... --chart-shadow` runs Lara's chart, then the upper-body chart (agent 1, which conditions 0x401 / 0x404 /
0x408 read), after every `World::tick` with the same `Actions` and world (input action timings kept by the shadow;
timeMult = 30 x the fixed tick, ignoring the combat time scale [I]) and logs each run where the chart's requested clip
differs from the controller's clip; the summary at `--frames` end lists the most evaluated unported conditions. The
support foot (player +0xF3C, condition 0x12D) comes from the anim events 0x34 / 0x35 / 0x36 of the clip Lara's layer
plays (lara.drm's event DTPs): the chart's own pattern clip on the runtime's clip clock (for a kind-2 request the pattern its node
plays), or when that is unresolved (S40's node 46) our controller's clip [I].
`--chart-trace FILE` writes the shared TSV (`tick state parent request stateTicks px py pz vx vy vz yaw inputs`, then
`t30=` the chart state time and `var_anim=` the chart clip clock): tick = the frame's index (`World::ticks() - 1`
after it: the tick the input script addressed), stateTicks = 60 Hz ticks since entering the state (0 on the entry tick,
also on a re-entry), position / velocity (units/s) / yaw (degrees) are ours, `inputs` is the hex mask of the same
tick's actions (1 Fwd, 2 Back, 4 Left, 8 Right, 0x10 Jump, 0x20 Interact, 0x40 Crouch, 0x80 Sprint, 0x100 Walk, 0x200
Grapple).

**Frame order** [O-runtime, U the poll's address]: tru.exe's `GAMELOOP_Frame` (0x5DFFE0) pumps the window messages (the
input actions' records +0 flags / +4 change time / +8 press time against the input clock 0xA02B68 +0x1C are updated
from them) before the game update, which runs the charts (0x768C50: agent 0, then agent 1), and increments the frame
counter gameTracker +0x24 at its end (0x5E003F). The Wine corpus injects a key between two frames and records it as held
on the next frame's row, and that row already shows the transition it causes (run_jump_bedroom tick 10: inputs 1 and
S40 -> S63). Ours in the same order within one tick: `--input-script` / the devices give tick N's `Actions`, then
`World::tick`, then the shadow's input timing and the charts; the trace labels the row N. (Before this the trace wrote
`World::ticks()` after the tick, N + 1, which looked like a one-tick input lag.)

**Input sources** (what each `ChartContext` read in `ChartShadow.cpp` is computed from). After cutover the chart drives
the controller, so a read taken from the controller's own state (its `State`, clip, aim or stamina) would feed the
chart its own past decisions. Rows marked *rebased* now come from geometry, physics, input or the chart's own stores;
the others are marked [I] with what blocks them.

**Kind-2 requests: the anim graph** [O]. 0x444BA0 kind 2 calls 0x443720(id, mirror) -> 0x43E250: the request id
indexes the object's graph node table (ObjectBase +0x50: 8-byte entries {DTP id of the node program, 0}; lara.drm
request 213 -> DTP 2248, 408 bytes; request 99 -> DTP 2134, 13 KB). A node is a program for a stack VM (0x432B20:
opcode = high byte; 0x02 push the next word, 0x01 pop, 0x47..0x5C float / bool arithmetic and compares, 0x63 jump,
0x64 jump if false, 0x65 call native [class, method] from table 0x8AC128, 0x7B return; 0x4370C0 pushes a frame). The
natives and how ours runs them: Runtime, "Anim request" above (`ChartRuntime::resolveRequest`). Module 1's natives
(table 0x8ABF90) push one player value: 4 +0xA80, 5 the jump target's owner flag else +0xEE8, 7 +0xED4 == 0 and not
game flag bit 26, 8 +0xEDC, 16 the context's held selector, 76 `canSprint()`. A selector's entries are blend nodes;
committing it (fn 3) queues one entry's records in order (0x4482C0 -> 0x446BD0; fn 4's static selector picks at random,
0x448320), and the chart hears the end when the queue drains (0x43E0C0). Game flag bit 26 is taken as clear (every Wine recording) [I elsewhere]. Not ported: the owner flag, a random pick between different entries, the selector object fn 4 pushes (0x88F26C; node 46's
891 branch queues three transition/loop pairs and fn 3 commits one), Play's two float arguments and flags.

### In-flight jump targets [O, not ported]

tru.exe keeps a free flight's jump target (player +0xA64 markup, +0xA68 param, +0x9F0 point) up to date while she is
in the air, where ours aims only at take-off:

- **Per frame**: action 510 (PSCAF_Airborne, on the flight chain S287) has Process **0x752410**: every frame it
  re-solves the velocity toward the target with the flight time left (+0x77C) through 0x73EDC0, and while a target is
  set and the time left exceeds player data +0xC24 it refines it with 0x751FC0 (0x751D10 + the markup lookahead
  0x72B5C0, rewriting +0xA74 / +0x77C and the target frame +0xA20..+0xA3C); it drops a jump-landing / beam target
  once she is falling (0x707500) and handles markup flagged 0x80000 through 0x769020.
- **New targets in flight**: action 230 (PSCPF_MarkUpAttach_SetAnimTarget, also on S287) runs **0x772CA0** as its
  PreAnimEntry and PreAnimReentry, i.e. on every state change inside the flight chain (S287 -> S288 -> S289 / S294
  ...): when bool property 0x199 is set and no target is held, it promotes the pending candidate player +0x3A0 (or
  +0x3E0, by a distance compare against her facing [I]) into +0xA64, with the target class from property 0x1A4 (else 0x19A).
  Transitions such as S289 T305 / the stick jump's S535 attach then see it through condition 0x262 (target class).
  Only these store to +0xA64 besides 0x741050 (a markup hand-off) and 0x771DB0 (reached from 0x6C0800, not the
  flight).
- **Candidate slots, every frame** [O]: the two 0x40-byte slots player +0x3A0 / +0x3E0 (markup, +4 param, +0x10
  point, +0x34 a float the player constructor 0x71C2D0 sets to -1) are filled by **0x710380**(instance, player +0x3A0,

  **0x71BFA0**, a process function listed in the player modes' table at 0x8ABA40 (0x1C-byte rows; it appears in
  36 rows). So the candidates are refreshed every frame by her collision move [I: in the air as on the ground, which
  rows are the flight modes not checked], and action 230 promotes one when a flight state is entered. Found through
  the address computations `add eax, 0x3A0` at 0x5D826A / 0x5D8C62 (the call sites); the condition at 0x764F51 reads
